# DECISIONS — импорт заказов маркетплейса

> Фикстура `frontend/public/marketplace-orders.json` — оригинал из задания. При копировании из PDF строки
> были разорваны переносами (`"1\n6:00"`, `"320\n0"`, `"B-10\n4"`); я склеил их обратно, больше ничего не менял.
> Копия для тестов бэкенда — `backend/tests/Fixtures/`; `make smoke` проверяет, что копии побайтно совпадают.

## 1. Как запустить

Нужен только Docker (Compose v2). Порты 8080 и 8000 должны быть свободны.

```bash
docker compose up -d --build      # или: make up
```

- UI: http://localhost:8080 — кнопка «Загрузить заказы» отправляет `marketplace-orders.json` из ассетов фронта.
- API напрямую: http://localhost:8000/api/shops/1/orders
- Миграции применяются при старте backend-контейнера: схема, затем отдельной миграцией — магазин №1 и его тарифы.

Проверки (на поднятом стеке; всё выполняется в контейнерах — локально не нужны ни PHP, ни Node):

```bash
make test            # всё ниже подряд
make qa              # PHP CS Fixer, PHPStan max, Rector dry-run (PHP 8.5 / Symfony 8.1), Deptrac (границы слоёв), doctrine:schema:validate
make test-backend    # PHPUnit: 139 тестов — юниты, интеграция на MySQL, API, CLI, конкурентный импорт 6 процессами
make coverage        # то же с покрытием (pcov): 100 % строк src/
make test-frontend   # ESLint (strict, typed) + Prettier + Vitest в docker build --target test: 23 теста, 100 % строк
make e2e             # Playwright: Pixel 7, iPhone 14 (WebKit), desktop + axe WCAG 2.1 AA; скриншоты в e2e/screenshots
make smoke           # e2e через nginx: импорт, повтор, 10 параллельных импортов, фильтр, смена статуса
make reset           # снести БД и поднять заново
```

Версии: PHP 8.5, Symfony 8.1, Doctrine ORM 3 / DBAL 4, MySQL 8.4 (последняя ветка 8.x — условие «MySQL 8»),
Angular 22 (standalone, signals, zoneless, `httpResource`), Node 24, PHPUnit 13, Vitest.

Результат на чистой машине (`docker compose down -v && make up && make test`): CS Fixer — 0 файлов к исправлению,
PHPStan max — 0 ошибок, Rector — 0 изменений, Deptrac — 0 нарушений, схема БД совпадает с маппингом, ESLint и Prettier без замечаний, 139 + 23 теста, smoke и e2e — OK.
Построчная сверка с ТЗ — в [SPEC-CHECK.md](SPEC-CHECK.md).

## 2. Ключевые решения

### Архитектура: слои и их границы

```
backend/src/
  Domain/          чистый PHP, ни одной зависимости от Symfony/Doctrine ORM
    Order/         агрегат Order (+OrderItem), OrderStatus, PhoneNumber, OrderLine, ReviewReason,
                   правило переходов статусов (Order::applyReportedStatus), порт OrderRepository
    Shop/          Shop, ShopRepository (порт; getForUpdate — блокировка)
    Delivery/      DeliveryCalculator + правила (Rule/*), тарифы, TariffRepository (порт)
  Application/     сценарии; вход и выход — только DTO
    Import/        ImportOrders + ImportOrdersCommand, порт MarketplaceOrderParser, ParsedOrder, MarketplaceStatus
    Import/View/   ImportReportView, ImportSummaryView, ImportResultView, RejectionView
    Order/         ListOrders + ListOrdersQuery
    Order/View/    OrderPageView, OrderView, OrderItemView, CustomerView, IntervalView, DeliveryView, ShopView
    Port/          TransactionManager
  Infrastructure/
    Persistence/   Doctrine-репозитории, транзакции, тип phone_number, XML-маппинг
    Marketplace/   адаптер маркетплейса: DTO записи (MarketplaceOrder/Customer/Delivery/Item) + Serializer + Validator
  UI/
    Request/       ImportRequest, OrderListRequest — DTO входа HTTP/CLI
    Http/          контроллеры (MapRequestPayload / MapQueryString → команда/запрос → Serializer), ошибки → JSON
    Cli/           app:orders:import
```

### Обмен данными между слоями — только DTO, через библиотеки Symfony

```
HTTP JSON ──Serializer + Validator (#[MapRequestPayload] / #[MapQueryString])──▶ UI\Request\*Request
          ──конструктор──▶ Application *Command / *Query
сырая запись маркетплейса ──Serializer (snake_case → camelCase)──▶ MarketplaceOrder DTO ──Validator──▶
          ──ObjectMapper (#[Map] на DTO)──▶ ParsedOrder ──use case──▶ Domain
Domain-сущность ──ObjectMapper (#[Map] на view)──▶ *View ──Serializer──▶ HTTP JSON
```

- **Вход HTTP**: `ImportRequest` и `OrderListRequest` заполняет и проверяет Symfony (Serializer + Validator),
  контроллер не видит `Request`. Из них собирается команда/запрос Application — у сценариев нет «голых» скаляров.
- **Запись маркетплейса** превращается в типизированный DTO через Serializer, а правила ТЗ описаны атрибутами
  Validator прямо на DTO. Код отказа (`missing_field`, `invalid_phone`, `unknown_status`…) лежит в `payload`
  ограничения, поле в ответе — путь нарушения в именах маркетплейса (`delivery.time_from`, `items[0].qty`).
  Парсер = 70 строк связки, без ручных `if`. Конвертация в `ParsedOrder` (копейки, московское время, `PhoneNumber`,
  позиции через `MapCollection`) — атрибутами ObjectMapper.
- **Выход Application** — `*View`, их строит ObjectMapper из сущностей по атрибутам `#[Map]`. UI больше не видит
  Domain: Deptrac теперь разрешает UI только Application (+Symfony), Application — Domain, PSR и ObjectMapper.
- **JSON-ответ** — сериализованный view; ручных массивов и презентеров нет. Формат ответа не изменился (фронт и
  e2e не трогал).
- Что Serializer не проверяет сам и пришлось задать явно: float `1.5` в `?int` он молча приводит к `1`
  (количество объявлено `int|float` + `Assert\Type('integer')`), строку вместо объекта позиции превращает в пустую
  позицию (до денормализации есть явная проверка формы `items[n]`).

- **Зависимости только внутрь**: UI → Application → Domain; Infrastructure реализует порты Domain/Application.
  Правила записаны в `backend/deptrac.yaml` и проверяются в `make qa` (Domain может зависеть только от
  `doctrine/collections` — ради to-many связи). Проверено мутацией: добавил атрибут Symfony в `Shop` —
  Deptrac выдал нарушение.
- **Маппинг ORM в XML** (`Infrastructure/Persistence/Doctrine/Mapping`), а не атрибутами: иначе Domain зависел бы от
  Doctrine. Цена — маппинг дальше от кода; `doctrine:schema:validate` в `make qa` подтверждает, что он совпадает с миграциями.
- **Сериализация — Serializer над view-DTO**: сущности не знают про JSON.
- **Исключения → HTTP в одном месте** (`ApiExceptionListener`): `UnknownShop` → 404; ошибки валидации DTO → код из
  `payload` первого нарушения (`invalid_batch`, `batch_too_large`, `invalid_query`), иначе `invalid_request`;
  битый JSON → 400 `invalid_json`. Контроллеры — по 2 строки.
- **Бизнес-правило статусов — в агрегате**: `Order::applyReportedStatus()` возвращает `Changed | Same | FinalKept`,
  use case только переводит это в исход импорта. Маппинг `DONE → delivered` — не домен, а словарь маркетплейса
  (`MarketplaceStatus` в Application).
- **Правила доставки без атрибутов фреймворка**: регистрация и порядок — в `config/services.yaml`.

### Современный PHP 8.5 / Symfony 8.1 — что именно и как проверено

- PHP: asymmetric visibility (`public private(set)`) в сущностях вместо геттеров, property hook
  (`OrderItem::$lineTotal`), pipe-оператор `|>` (`PhoneNumber`), `#[\NoDiscard]` на методах, результат которых
  нельзя игнорировать (`applyReportedStatus`, `quote`), `(void)`-каст в тесте, typed class constants, `readonly`
  классы для VO и сервисов, `#[\Override]`, `array_any`, `new Foo()->bar()` без скобок.
- Symfony: invokable-контроллеры с `#[Route]` на классе, `#[MapQueryString]` + Validator для query,
  invokable-команда с `#[Argument]` и `SymfonyStyle`, `#[AsEventListener]`, `!tagged_iterator` с приоритетами.
  Doctrine ORM 3 с native lazy objects (PHP 8.4+) — поэтому asymmetric visibility в сущностях безопасна.
- **Проверка инструментами, а не на словах**: Rector с `withPhpSets()` (до PHP 8.5 из composer.json),
  `withComposerBased(symfony, doctrine, phpunit)` (наборы под установленные версии) и prepared-наборами
  dead code / code quality / type declarations — dry-run даёт 0 изменений. PHP CS Fixer: `@PER-CS`, `@Symfony`,
  `@Symfony:risky`, `@PHP8x5Migration(:risky)`. PHPStan level max + strict-rules + phpstan-symfony/doctrine/phpunit
  (Doctrine-расширение читает реальный XML-маппинг и проверяет DQL).
- `#[MapRequestPayload]` для импорта принимает только конверт `{"orders": [...]}`; сами записи остаются сырыми
  и разбираются по одной в адаптере — так один битый заказ отклоняется отдельно, а не роняет всю пачку.
- Symfony ObjectMapper принимает в `transform` объект-колбэк только с интерфейсом `TransformCallableInterface`,
  поэтому в `#[Map]` колбэки записаны как `[Class::class, 'method']`, а не first-class callable `Class::method(...)`.
- `Assert\When` с замыканием в атрибуте — замыкания в константных выражениях появились в PHP 8.5.


### Идемпотентность и конкурентность (самое важное)

**Чем гарантировано отсутствие дублей:** двумя слоями.

1. `UNIQUE (shop_id, external_id)` в `orders` — физическая гарантия: второй строки быть не может никогда, что бы ни случилось в коде.
2. Весь импорт пачки — одна транзакция, которая первым делом берёт `SELECT … FROM shop WHERE id = ? FOR UPDATE`.
   Импорты **одного магазина** сериализуются; разные магазины друг другу не мешают.

**Что увидит второй запрос:** он подождёт на блокировке (миллисекунды — пачка маленькая), затем прочитает уже
закоммиченные заказы и получит нормальный отчёт: `unchanged` для всех, что создал первый. Не 409, не 500 — тот же
формат ответа, по которому магазин понимает, что произошло.

**Почему не только unique-индекс.** Проверено мутационно: убрал блокировку — `ConcurrentImportTest` (6 процессов
одновременно) падает с `1062 Duplicate entry` у проигравших запросов. Дублей в БД нет, но пользователь получает
ошибку вместо отчёта. С блокировкой — все запросы 200, создал ровно один.

Рассмотренные варианты:
- `INSERT … ON DUPLICATE KEY UPDATE` — атомарно, но правило «меняется только статус, финальный не откатывается» и
  «вернуть created/updated/unchanged» превращаются в SQL-акробатику; плюс позиции заказа — отдельная таблица.
- `SELECT … FOR UPDATE` по заказу + ретрай на deadlock/duplicate — в InnoDB на несуществующих строках это gap-locks
  и дедлоки; работает, но сложнее объяснить и протестировать.
- `GET_LOCK()` — рабочий вариант, но блокировка живёт вне транзакции, легко забыть отпустить.
- Idempotency-Key + таблица запросов — решает другую задачу (повтор того же HTTP-запроса после обрыва сети).
  Здесь бизнес-ключ уже есть (магазин + id), а повторный импорт по правилам и так безопасен. **Не делал.**

Двойной клик закрыт ещё и на фронте (кнопка `disabled` на время запроса + guard в `run()`), но это UX, не гарантия.

### Данные

- **Деньги** — целые копейки (`INT`). Парсинг рублей из JSON без float-арифметики: число → строка → regex
  `^\d+(\.\d{1,2})?$` → копейки. `1990.555` — отказ, а не тихое округление.
- **Время** — в БД `DATETIME` в UTC (`date.timezone=UTC` в контейнере, явный `setTimezone(UTC)` при парсинге).
  Время из фикстуры без смещения трактуется как `Europe/Moscow`; явное смещение (`Z`, `+05:00`) уважается.
  API отдаёт ISO 8601 с `+00:00`; фронт показывает в часовом поясе магазина (`shop.timezone`), а не устройства —
  курьер в другом поясе должен видеть те же «14:00–16:00».
- **Позиции** — отдельная таблица `order_item` (название, qty, цена за единицу, позиция). JSON-колонка проще,
  но позиции — это данные, по которым потом считают отчёты/остатки.
- **Доставка заморожена в заказе**: `delivery_cost`, `delivery_breakdown` (JSON: строки расчёта), `grand_total`.
- **Индексы**: `UNIQUE(shop_id, external_id)` — идентичность и поиск при импорте;
  `(shop_id, status, id)` — фильтр по статусу + сортировка по id без filesort; FK-индекс `shop_id` (в InnoDB
  неявно `(shop_id, id)`) — список без фильтра; `UNIQUE(shop_id, district)` в тарифах.

### Миграции

- **Схема генерируется, а не пишется руками**: маппинг → `bin/console doctrine:migrations:diff` → ревью → коммит.
  Справочные данные (магазин №1, тарифы с названиями районов) — отдельной миграцией, сделанной через
  `doctrine:migrations:generate`: схема и данные откатываются и читаются независимо.
- Schema API (`$schema->createTable()`) не использую: проект под одну СУБД, а diff и так строит SQL из маппинга;
  данные через билдер всё равно не описать.
- `make qa` накатывает миграции на тестовую БД и запускает `doctrine:schema:validate`: если маппинг поменяли без
  миграции, проверка падает (проверено мутацией).
- **Ревью сгенерированного SQL нашло баг**: без явной collation MySQL 8.4 сравнивает строки регистронезависимо
  (`utf8mb4_0900_ai_ci`), и уникальный индекс считал `MP-1` и `mp-1` одним заказом, а дедупликация в PHP — разными.
  Пачка с такими id падала на `1062 Duplicate entry` → 500 на весь импорт. id маркетплейса — идентификатор,
  поэтому `external_id` теперь `utf8mb4_bin`; тест `testExternalIdIsCaseSensitive` сначала воспроизвёл падение,
  потом прошёл. В первой версии миграции SQL был написан вручную с `utf8mb4_unicode_ci` — та же проблема, просто
  незаметная.

### Расчёт доставки

- **Когда:** при импорте, один раз. Цена — часть заказа, который клиент уже оплатил на площадке; если завтра
  тариф поменяют, старые заказы не должны молча подорожать. При чтении ничего не считается.
- **Где тарифы:** таблица `delivery_tariff` (на магазин). Надбавка за срочность (200 ₽) и окно (120 мин) —
  параметры в `config/services.yaml`: по условию они одинаковы для всех районов.
- **Новое правило** = новый класс в `Domain/Delivery/Rule`, реализующий `DeliveryRule`
  (`apply(DeliveryContext): ?DeliveryCharge`), + одна запись в `services.yaml` с тегом и `priority` (порядок строк
  расчёта). Домен не знает про DI-атрибуты. Каждое правило даёт строку расчёта, сумма строк —
  стоимость. Расшифровка сохраняется в заказ и видна в UI (подсказка над ценой, бейдж «срочно»).
- «Бесплатная доставка обнуляет только базовую цену» — следует из структуры: база и срочность — разные правила.

### API

```
POST /api/shops/{shopId}/imports      тело — файл маркетплейса как есть: {"orders": [...]}
GET  /api/shops/{shopId}/orders?status=new&page=1&perPage=20
```

- Магазин в пути: авторизации нет, а в реальности shopId придёт из токена — замена в одном месте.
- Ответ импорта — **200 всегда, когда пачка обработана**, даже если все записи отклонены: сам импорт успешен.
  `summary` (счётчики по исходам) + `results[]` в порядке файла: `index`, `externalId`, `outcome`
  (`created|updated|unchanged|duplicate|rejected`), `orderId`, `status`, `previousStatus`,
  `reason {code, message, field}`, `notes[]` (пометки: `total_mismatch`, `final_status_kept`, `duplicate_in_batch`…).
  `code` — для машины, `message` — по-русски для магазина, `field` — для отладки.
- Ошибки — единый JSON `{"error": {"code", "message"}}`: 400 `invalid_json` / `invalid_query` (неизвестный статус, `page < 1`, `perPage` вне 1..100 — с перечнем нарушений),
  422 `invalid_batch` (нет `orders`, в том числе голый массив) / `batch_too_large` (>1000), 404 `shop_not_found`, 500 `internal_error` (без деталей наружу).
- Пагинация — offset (`page`/`perPage` ≤ 100, проверяется Validator через `#[MapQueryString]`) + `total` + `statusCounts` для чипов фильтра.
  Список — двумя запросами: id страницы, затем заказы с позициями fetch-join (без N+1 и без LIMIT по JOIN).

### Фронтенд

- Один экран: кнопка импорта → отчёт → список. Angular 22: standalone, signals, zoneless, OnPush, `httpResource`
  для списка (перезапрашивается сам при смене фильтра/страницы), `linkedSignal`, чтобы при смене фильтра не мигал
  пустой экран.
- **Структура по фиче** `src/app/orders/`: модели, `OrdersApi`, `OrdersStore` (состояние списка на signals — его
  читают и список, и шапка, а панель импорта вызывает `reload()`; родитель не лезет в дочерний компонент через
  `viewChild`), pipes форматирования (`money`, `phone`, `district`, `deliverySlot`) вместо вызова функций в шаблоне,
  компоненты с отдельными `.html`/`.scss` (стили компонента инкапсулированы, глобально — только токены и общие
  элементы), подписка с `takeUntilDestroyed`, без `!` в шаблонах (`@if (x; as y)`, `@let`).
- **Линтер**: `angular-eslint` + `typescript-eslint` strictTypeChecked: OnPush, signals, `inject()`,
  `takeUntilDestroyed`, лимит inline-шаблона, запрет `!` в шаблонах, доступность шаблонов; Prettier — проверка
  формата. Оба в `make test-frontend`. Линтер нашёл устаревший в Angular 22 `withFetch()` (Fetch теперь по
  умолчанию) и неразрывные пробелы, вставленные в регулярку символами, а не escape-последовательностями.
- **Состояния**: импорт — idle / загрузка (спиннер, кнопка заблокирована) / отчёт / ошибка (сеть отдельно от
  ошибки API) с «Повторить». Список — загрузка / пусто до первого импорта / пусто по фильтру / ошибка / данные,
  «устаревшие» данные полупрозрачны во время перезагрузки.
- **Отказы**: по умолчанию в отчёте показаны **только проблемные** записи (отклонённые, дубли, с пометками) —
  на телефоне полный отчёт выталкивает список заказов за экран. «Показать все» и чипы-счётчики фильтруют отчёт.
- **Телефон**: mobile-first. Карточки до 900px, таблица (CSS grid, та же разметка) — шире. Чипы статусов
  скроллятся горизонтально, кнопка импорта во всю ширину и 48px высотой, телефон покупателя — `tel:`-ссылка.
  Проверено в браузере на 375px: нет горизонтального скролла.
- Без UI-библиотек: ~5 КБ CSS, дизайн не оценивается.
- Дизайн-ревью после первой версии: расшифровка доставки была только в `title` (на телефоне не видна) — заменил
  на `<details>` «Состав и расчёт» с позициями, SKU, строками доставки и итогом площадки при расхождении;
  районы по-русски («Север», а не `north`); `aria-pressed` у чипов фильтра; название магазина в шапке;
  отменённые заказы приглушены.

### Тесты: что сломается первым и незаметнее всего

**Время и деньги.** Ошибка в часовом поясе на ±3 часа не роняет ничего — она тихо добавляет или убирает 200 ₽
срочности. Float в деньгах тихо даёт `4280.999`. Граница «ровно 2 часа» и «ровно порог» — классический off-by-one.
Поэтому основной вес тестов здесь:

| Уровень | Что | Где |
|---|---|---|

## 3. Что сознательно не сделал и чем это рискует

- **Хранение истории импортов** (кто, когда, какой отчёт). Риск: «почему вчера отклонили заказ» — только из логов.
  Добавляется таблицей `import_batch` + JSON отчёта, без изменения логики.
- **Idempotency-Key на HTTP**. Риск: при обрыве сети повтор вернёт `unchanged` вместо исходного `created`.
  Для бизнеса результат тот же — дублей нет.
- **Оптимистичная/ручная правка заказа, история статусов** — вне задачи.
- **Рантайм** — FrankenPHP в worker-режиме с `APP_ENV=prod`, как в официальном шаблоне symfony-docker:
  Symfony Runtime поддерживает его напрямую, состояние сервисов (EntityManager) сбрасывается между запросами.
  Первая версия работала на встроенном сервере PHP — он не предназначен для продакшена, заменил при ревью.
  Остались компромиссы: миграции на старте контейнера (для нескольких реплик — отдельный шаг деплоя) и
  `APP_SECRET` в `.env` (в реальном окружении — Symfony secrets).
- **Keyset-пагинация** — offset достаточно для списка заказов одного магазина; на сотнях тысяч — `WHERE id < ?`.
- **Большие пачки**: одна транзакция на всю пачку, лимит 1000. Риск: при неожиданной ошибке БД откатывается вся
  пачка (валидационные отказы на это не влияют — они до транзакции). Для больших файлов — чанки по N заказов.
- **Перерасчёт доставки при повторном импорте** — по правилу 5 меняется только статус; если площадка исправит
  позиции, мы этого не увидим. Это осознанное следствие правила, а не недосмотр.
- **CI, авторизация, i18n** — не нужно по условию.
- **Playwright e2e в браузере** — вместо него `smoke.sh` по API + ручная проверка в браузере на 375px и desktop.
  Риск: регресс вёрстки ловится только глазами.

## 4. Допущения в неоднозначных местах

### Что даёт оригинальная фикстура (11 записей) и почему

| Запись | Исход | Расчёт / причина |
|---|---|---|
| MP-1001 | создан | centre, 3 200 < 5 000 → 300 ₽; до слота 2 дня → без срочности. Итого 3 500 |
| MP-1002 | создан | north, 5 000 < **7 000** (порог центра 5 000 тут не действует) → 400 ₽; создан 11:00, слот 12:00 → +200. Итого 5 600 |
| MP-1003 | создан | centre, 6 400 ≥ 5 000 → доставка 0. Итого 6 400 |
| MP-1004 | создан | самовывоз, телефон `8 900 444 33 22` → `+79004443322`. Итого 1 500 |
| MP-1005 | создан сразу `delivered` | south 400 ₽. Итого 3 200 |
| MP-1006 | отклонён `unknown_district` | района `zarechye` нет в тарифах |
| MP-1007 | отклонён `invalid_phone` | `123` |
| MP-1008 | отклонён `unknown_status` | `PACKING` нет в контракте |
| MP-1009 | создан, «нужна проверка» | 2 × 1 800 = 3 600 ≠ total 3 000; считаем от 3 600; suburb 700 (бесплатной нет). Итого 4 300 |
| MP-1001 (повтор) | дубль | первое вхождение уже обработано |
| MP-1010 | создан `cancelled` | centre 300 ₽. Итого 2 300 |

Трактовки, которые потребовала именно эта фикстура:

| Место | Трактовка | Почему |
|---|---|---|
| Слот = `date` + `time_from`/`time_to` без пояса | московское время магазина | «время — московское»; у `created_at` пояс явный (`+03:00`), у слота — нет |
| Слот через полночь | невозможен (`time_to <= time_from` → `invalid_interval`) | дата в слоте одна |
| Время `9:00` | принимается как `09:00`; `24:00` — отказ | формат часов — шум, 24:00 — уже другой день |
| Заказ впервые приходит сразу `DONE`/`CANCELED` (MP-1005, MP-1010) | сохраняется с этим статусом и с рассчитанной доставкой | правило 5 запрещает откат *при повторном* импорте; при первом статус просто берём. Цена нужна для истории/выручки; отменённому её можно не показывать — решение UI, не данных |
| Слот в прошлом относительно момента импорта (MP-1005, MP-1010) | не ошибка | срочность считается от `created_at`, а не от «сейчас» — иначе повторный импорт менял бы цену |
| `sku` | сохраняется в позиции, не обязателен | не в списке обязательных; пригодится для сверки с каталогом |
| Полный дубль (MP-1001 дважды с одинаковыми данными) | `duplicate`, без сравнения содержимого | правило 5: повтор id в пачке — дубль, независимо от данных |

### Общие трактовки правил

| Место | Трактовка | Почему |
|---|---|---|
| `created_at` без смещения | Москва (`Europe/Moscow`); со смещением — как указано | так сказано в задании; смещение надёжнее догадки |
| «Меньше чем через 2 часа» | строго `< 120 мин`; ровно 2 ч — не срочно | буквальное прочтение |
| Интервал начался раньше `created_at` | срочно (+200) | «меньше 2 часов» включает отрицательное; заказ при этом валиден |
| «Бесплатно от суммы» | `сумма позиций >= порог` | «от 5000» включает 5000 |
| Порог бесплатной доставки | по сумме позиций, не по `total` | правило 6: «для расчётов берём сумму позиций» |
| `total` отсутствует | заказ сохраняется, «нужна проверка» (`total_missing`) | сверить не с чем — пусть посмотрит человек |
| `created_at` отсутствует у доставки | заказ сохраняется без надбавки, «нужна проверка» | поле не в списке обязательных, но без него срочность не определить |
| Телефон | `+7…`, `7…`, `8…` (11 цифр) + пробелы/дефисы/скобки; 10 цифр без кода, `+8…`, текст — отказ | в правиле перечислено, что принимаем; остальное не угадываем |
| Статус | без учёта регистра и пробелов (` done ` = `DONE`); `CANCELLED` (британское) — отказ | регистр — шум, другое слово — уже другой контракт |
| Район | без учёта регистра (`North` = `north`) | то же |
| Id | строка; число `77` и `" 77 "` — один и тот же заказ | id маркетплейса — идентификатор, не число |
| Число там, где по контракту строка (например, `address: 12`) | отказ `invalid_payload` с полем | типы проверяет Serializer на границе; угадывать, что имела в виду площадка, не стал (исключение — `id`: число и строка) |
| Дубль, если первое вхождение отклонено | второе всё равно `duplicate` | «первое обрабатывается обычно» — первое и было обработано (отклонено); иначе результат зависел бы от порядка ошибок |
| Повторный импорт с невалидными данными | запись отклоняется, статус **не** меняется | не доверяем частично битой записи |
| Повторный импорт, а тариф района удалён | статус обновляется | тариф нужен только при создании; цена заморожена |
| Нефинальный статус «назад» (`delivering → new`) | разрешено | правило запрещает откат только из финальных |
| `delivered → cancelled` | запрещено (`unchanged` + пометка `final_status_kept`) | оба финальные |
| Самовывоз с районом/адресом | район игнорируется, доставка 0 | для самовывоза они не нужны |
| Цена позиции 0 | допустима (подарочная упаковка) | отрицательная и >2 знаков после запятой — отказ |
| Количество | целое > 0 | 1.5 букета не бывает |
| Несколько ошибок в записи | возвращается первая | магазину нужна причина, а не валидатор; собрать все — небольшая доработка |

## 6. Как использовал AI и что переделывал

Работал с Claude Code: генерация скелетов, первые версии классов и тестов, вёрстка. Проверял за ним: каждую
трактовку правила (они в таблице выше — это мои решения, не модели), SQL-схему и индексы, места с деньгами и временем.

Что пришлось переделать / что поймали:
- **Ошибки в тестах, а не в коде**: подсчёт позиций (ожидалось 6, на деле 7 — у двух заказов по 2 позиции);
  помощник приводил к `int` всё «числовое», включая телефон `+7…`.
- **Деньги на фронте**: `Intl` с `minimumFractionDigits: 0` выводил `4 281,5 ₽`. Найдено тестом, исправлено.
- **Вёрстка**: grid-ячейка растягивалась под чипы — горизонтальный скролл на 375px. Найдено в браузере.
- **Angular-тесты**: `whenStable()` зависал, пока открыт запрос `httpResource` — сначала `flush`, потом ожидание.
- **UX отчёта**: первая версия показывала все 11 строк отчёта; на телефоне список заказов уезжал за экран —
  переделал на «только проблемные по умолчанию».
- **Сообщения**: в отказах было техническое `delivery.address` — заменил на «адрес доставки», машинное имя оставил в `field`.
- **Мутационная проверка**: убедился, что тест конкурентности действительно падает без блокировки — иначе он
  мог бы проходить «случайно». Так же проверил Deptrac.
- **Автоматика тоже ошибается — Rector дважды сломал Doctrine**, тесты поймали оба раза:
  удалил `OrderItem::$order` как «неиспользуемое» свойство (он не видит XML-маппинг; `Order` при этом продолжал
  передавать `$this` → TypeError) и сделал `readonly` коллекцию `$items`, которую Doctrine подменяет на
  `PersistentCollection`. Первое исправил публичным чтением (`public private(set)`), второе — исключением правила
  для сущностей в `rector.php`.
- **Инструменты спорили между собой**: Rector (`$this->assertX`) против CS Fixer (`self::assertX`) и
  PHPStan strict-rules (запрет динамического вызова статики). Выбрал стиль из документации PHPUnit (`$this->`),
  выровнял CS Fixer, отключил одно правило strict-rules с объяснением. В `src/` у PHPStan нет ни одного ignore;
  в интеграционных тестах игнорируется только `mixed` из декодированного JSON/строк БД.
- **Ложное срабатывание PHPStan**: считал `$this->json()` чистым и «запоминал» результат между запросами —
  помечен `@phpstan-impure`.
